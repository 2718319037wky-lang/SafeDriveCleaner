# 安全设计说明与失效模式分析

本文档回答一个问题：**这个工具凭什么可以被信任去删数据？**

## 一、根本取舍：白名单制，而非黑名单制

黑名单式清理脚本的失效模式是**沉默的**：全盘扫描 → 排除一批已知目录 → 把剩下的删掉。任何「没被想到」的目录都会被当成垃圾。而「没想到」恰恰是必然的——每个用户的目录结构都不一样。

SafeDriveCleaner 采用白名单制：候选集合**只能**来自 `config/rules.default.json` 中显式列出的 pattern。

由此得到一个重要性质：

> **误删的唯一致因，是配置里多了一条不该有的规则。**
> 而「某个目录因为没人想起它而被删」这种失效模式，在架构上不可能发生。

代价是覆盖率：它清不掉你手工堆在 `D:\乱七八糟` 里的临时文件。这是刻意的取舍。

## 二、五道防线

```
候选来源:  rules.default.json 白名单 pattern 匹配
              │
              ├─[1] 范围校验 ──── 必须在目标根目录之下；不得是根目录本身
              │
              ├─[2] 路径保护 ──── neverTouchPaths          (等于或位于其下 → 拒绝)
              │
              ├─[3] 名称保护 ──── neverTouchDirectoryNames (目标叶子名命中 → 拒绝)
              │                    + neverTouchPathSegments (路径段命中 → 拒绝)
              │                    + neverTouchExtensions   (文件扩展名命中 → 拒绝)
              │
              ├─[4] 链接保护 ──── 目标自身或其根下祖先为 reparse point → 拒绝
              │                    遍历时也不进入任何 reparse point
              │
              ├─[5] 年龄校验 ──── minAgeDays 阈值，未达则跳过
              │
              ▼
         统计体积 → 展示 → 交互确认
              │
              ├─[6] 执行前复查 ── 存在性 + 实际类型 + 四道保护裁决全部重跑
              │                    （防住"扫描到执行之间路径被掉包"）
              │
              ├─[7] 占用检测 ──── 文件型目标被独占则跳过并说明原因
              │
              ▼
         移入回收站 → 删除后二次校验（Test-Path 确认真的没了）
```

**无绕过机制**：这四道保护不接受任何来自规则的例外。下面几个设计细节值得单独说明。

## 三、三个踩过的坑（都已在代码里写死）

这三个坑都是在本项目自测中真实踩到并修复的，记录下来是因为它们都很隐蔽。

### 1. 不要把裸 `{ROOT}` 写进 `neverTouchPaths`

`neverTouchPaths` 的判定语义是「目标**等于**该路径，**或位于该路径之下**」。把根目录写进去，等于拦下根目录下的所有候选——扫描结果永远是空的，但工具不会报错。

**这是最危险的一类失效模式：看起来「盘很干净」，实际是「一个都没放过」。**

缓解：
- 默认配置里已移除裸 `{ROOT}`；
- `Import-CleanerProtection` 会检测展开后等于根目录的条目，自动剔除并打印 `WARN`；
- 「目标是根目录本身」由引擎硬编码拒绝（返回 `E_ROOT`），无需也无法用配置表达；
- 测试 `T6f`（合法目标必须放行）+ `T8c`（必须真删掉东西）就是防这类「假绿灯」的。

### 2. `.db` 扩展名保护会误伤 `Thumbs.db`

扩展名保护名单里有 `.db`（防止误删数据库）。而 Windows 缩略图缓存恰好叫 `Thumbs.db`。结果：缩略图规则永远命中不了任何东西。

缓解：新增 `neverTouchExtExceptions`，做**文件名级**例外：

- 只按完整文件名精确匹配，不支持通配符，无法被规则间接利用；
- 其余三道保护依然全部生效；
- 例外文件仍必须被某条白名单规则显式命中，才可能成为候选。

### 3. 默认 `MaxDepth` 太小会静默漏掉缓存

真实缓存路径很深：

```
\Users\<名>\AppData\Local\Google\Chrome\User Data\Default\Cache     ≈ 9 层
\Users\<名>\AppData\Roaming\JetBrains\IntelliJIdea2024.1\caches     ≈ 8 层
```

如果 `MaxDepth` 是 6，这些路径根本走不到，而且**不会报错**——又是一次「假绿灯」。

缓解：
- 默认 `MaxDepth` 提高到 10；
- 新增**深度截断告警**：遍历中若某目录到达深度上限且仍有子目录，会记录并在日志、控制台、HTML 报告卡片三处告警。宁可多说一句「可能漏了」，也不能让用户以为已经扫干净了；
- 测试 `T2b`/`T2c` 守住这两点。

## 四、失效模式清单

| # | 失效模式 | 后果 | 缓解措施 |
|---|---|---|---|
| F1 | 规则 pattern 写错，匹配到用户数据 | 误删 | 四道保护拦截；诱饵测试 T3 |
| F2 | 裸 `{ROOT}` 进保护清单 | 候选恒为空，假绿灯 | 自动剔除 + WARN；T6f / T8c |
| F3 | 盘上有 `D:\cache -> C:\Users\me` 之类链接 | 跨盘误删外部数据 | 遍历与裁决双重拒绝 reparse point；T4a / T4b / T8b |
| F4 | `MaxDepth` 不足 | 静默漏报，假绿灯 | 默认 10 + 截断告警；T2b / T2c |
| F5 | 删掉正在被程序占用的缓存 | 程序异常 / 删除失败 | `minAgeDays` 阈值 + 逐条错误捕获不中断；T5 / T8d |
| F6 | 误删了想恢复的内容 | 数据丢失 | 默认走回收站 + JSON 报告记录原始路径 + 还原脚本 |
| F7 | 脚本文件编码不对 | 中文乱码 → 语法错误 → 行为不可预期 | 全量 UTF-8 BOM 校验纳入静态测试 |
| F8 | 自动化里误用 `-Yes` 配 `Permanent` | 不可还原的删除 | `Permanent` 必须单独输入 `PERMANENT`；`-Yes` 同时使用会打印醒目 WARN |
| F9 | 扫描后到执行前路径被掉包（TOCTOU） | 误删 / 穿过链接删到盘外 | 执行前逐条复查：存在性 + 实际类型 + 完整四道保护裁决重跑；T10d / T10e |
| F11 | 规则声明的 targetType 与目标实际类型不符 | 删掉文件却按 0 字节统计，回收站回退实现直接报错 | 裁决阶段做实际类型校验，不一致返回 `E_TYPE`；T10a / T10b |
| F12 | 有人写出 `{ROOT}\**` 这类"匹配一切"的过宽白名单 | 白名单制的前提被架空 | 加载规则时识别并告警；T10c1–T10c3 |
| F13 | 回收站接口不可用时"退化为永久删除" | 不可还原的数据丢失 | 探测到不可用即中止，绝不降级；`Auto` 与 `RecycleBin` 行为一致 |
| F10 | 接口报告成功但实际没删掉 | 报告与事实不符 | 删除后 `Test-Path` 二次校验，不一致记为 `Failed` |

## 五、工具明确不做的事

- **不做注册表清理。** 注册表没有回收站，误删不可还原。
- **不做卸载残留清理。** 需要判断「哪个软件已卸载」，误判概率高。
- **不做「重复文件」自动删除。** 同名同大小的文件未必等价，判定不可靠。
- **不永久删除（除非你显式指定 `-DeleteMethod Permanent` 并二次确认）。** 默认永远是回收站。
- **不联网、不上传任何信息。** 纯本地工具，无遥测。

## 六、如何在别的盘上安全试跑

想先拿 C 盘或其他目录试水，推荐这条路径：

```powershell
# 1) 先看保护清单会不会误伤（只读）
.\Clean-DDrive.ps1 -Drive C -Mode Scan -Trace

# 2) 看报告里的「安全防线记录」和「深度截断告警」两节
#    如果截断告警不为 0，提高 -MaxDepth 重跑

# 3) 预演，逐条确认候选路径
.\Clean-DDrive.ps1 -Drive C -Mode Clean -DryRun

# 4) 先只拿一两个低风险分类试
.\Clean-DDrive.ps1 -Drive C -Mode Clean -Categories 缩略图缓存

# 5) 确认无误后再放开
.\Clean-DDrive.ps1 -Drive C -Mode Clean
```

第 1 步的 `-Trace` 会把**每一条被跳过的候选及其原因**打进日志，这是审查保护规则是否合理的最快方式。

## 七、修改保护配置后必须做的事

```powershell
.\tests\Test-Syntax.ps1
.\tests\Run-Tests.ps1
```

`Run-Tests.ps1` 的 39 项断言里，有一半是**反向断言**（诱饵必须活下来、沙箱外必须零变化）。改动保护清单后如果这些断言仍然全绿，才说明改动没有打开缺口。
